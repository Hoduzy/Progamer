# 챔피언 이미지가 이니셜로만 나오던 문제

증상: 밴픽 화면에서 애쉬·잔나·나미·밀리오·쓰레쉬·레오나·브라움·리 신 같은 챔피언이 이니셜(글자)로만 나오고, 같은 화면의 애니·니코는 정상. 아이패드 사파리.

## 1. 원인 확인

### 요청 URL은 정상이었다
- 밴픽 화면(1180×820, 크롬)에서 실패한 요청을 모두 찍어 봄 (`[img]` 콘솔 로그, 요청 실패 이벤트).
- 만들어진 주소는 전부 `https://ddragon.leagueoflegends.com/cdn/16.23.1/img/champion/<id>.png` 형태로, **버전이 undefined이거나 id가 빈 주소는 없었다.** 애쉬 `Ashe`, 잔나 `Janna`, 리 신 `LeeSin` 모두 champion.json의 id와 같다.
- 크롬에서는 117칸 모두 성공(실패 0). 즉 이름·주소 문제가 아니라 **요청이 실패했을 때의 처리** 문제.
- 실제 배포 주소를 검사하던 중에도 서비스 워커를 거친 요청 몇 개가 `net::ERR_FAILED`로 실패한 적이 있다(브라움·쓰레쉬·노틸러스·뽀삐·렉사이 — 모두 같은 시점에 한꺼번에 요청된 서포터 목록). 사파리에서 같은 일이 더 자주 생긴 것으로 본다.

### 실패를 영구히 굳히는 코드가 두 군데 있었다
1. **서비스 워커가 상태를 모르는 응답(opaque)까지 저장**: `<img>`가 CORS 없이 요청하면 서비스 워커는 응답 상태(200인지 오류인지)를 볼 수 없다. 기존 코드는 `res.ok || res.type === 'opaque'`이면 캐시에 넣었으므로, 한 번 잘못 받은 응답이 저장되면 **그 챔피언은 이후 계속 캐시의 깨진 응답을 받아 이니셜로 나왔다.** 특정 챔피언만 매번 안 뜨는 증상과 맞는다.
2. **`onerror`에서 바로 이니셜로 교체, 다시 시도 없음**: 요청이 한 번 실패하면 그 자리를 영구히 이니셜로 바꿨다.

### 한꺼번에 요청
- 밴픽 목록은 100칸이 넘는데 `loading="lazy"`만 걸고 동시 요청 수 제한이 없었다. 아이패드 사파리는 한꺼번에 많이 요청하면 일부를 실패시킨다.

### 순서 문제
- 앱 시작 때 Data Dragon 버전·champion.json을 기다린 뒤 첫 화면을 그리므로 순서 자체는 맞았다. 다만 이미지 주소를 **화면을 그리는 순간** 만들었기 때문에, 버전을 받기 전에 그려지는 경우가 생기면 주소가 잘못될 수 있는 구조였다.
- 이제 화면은 `<img class="lz" data-k="champ" data-id="Ashe">` 자리만 그리고, **주소는 이미지 로더가 Data Dragon 준비가 끝난 뒤(`setResolver`)에 만든다.** 준비 전에는 아무 요청도 보내지 않는다.

# 홈 화면 앱에서 이미지가 하나도 안 뜨던 문제

증상: 아이패드에서 홈 화면에 추가한 앱으로 열면 게임 이미지가 하나도 안 뜨고, 사파리 탭에서는 대부분 뜸.

## 원인 확인

| 확인한 것 | 결과 |
|---|---|
| 서비스 워커의 다른 도메인 이미지 처리 | **원인.** 캐시에 없는 이미지를 받으면 `await fetch()` 뒤에 `e.waitUntil(cache.put(...))`을 불렀다. 크롬은 `respondWith`가 진행 중이면 이걸 허용하지만, **사파리(WebKit)는 fetch 이벤트 처리가 끝난 뒤 부른 `waitUntil`에 오류(InvalidStateError)를 던진다.** 그러면 `respondWith`에 넘긴 작업 전체가 실패해 이미지 요청이 네트워크 오류가 되고, 캐시에 저장도 안 되므로 **다시 시도해도 매번 같은 이유로 실패**한다. 홈 화면 앱은 처음부터 모든 요청이 서비스 워커를 거치므로 하나도 안 뜨고, 사파리 탭은 서비스 워커가 아직 페이지를 관리하지 않았거나 예전 서비스 워커일 때가 있어 대부분 떴던 것. |
| 불투명 응답(opaque, status 0) | 바로 앞 수정(v2)에서 `crossorigin="anonymous"`로 바꿔 이미지 응답이 opaque가 아니었고, `response.ok` 검사로 에러를 던지지는 않았다. 다만 opaque 응답은 저장하지 않았으므로 CORS 없이 받은 이미지는 오프라인에서 못 썼다. |
| manifest.json `start_url`·`scope` | `"./"`·`"./"` — 저장소 하위 경로(`/Progamer/`)에 맞는 상대 경로. 문제 없음. |
| 이미지를 fetch()→blob으로 받는 코드 | 없음 (`<img>` 요소로 직접 불러옴). |

이 환경에는 사파리(WebKit)가 없어 사파리 오류를 직접 재현하지는 못했다. 크롬에서 같은 코드 경로를 검사했고, 사파리에서 문제가 되는 비동기 `waitUntil` 호출 자체를 없앴다.

## 수정
- **서비스 워커 (`sw.js`)**
  - 다른 도메인(Data Dragon·Community Dragon): **네트워크 먼저, 실패하면 캐시.** 둘 다 실패할 때만 에러를 넘긴다 (404 같은 오류 응답은 그대로 넘겨 화면의 로더가 다시 시도).
  - 캐시 저장은 응답과 분리(`waitUntil` 안 씀). 저장 조건: 같은 도메인은 200만(설치 때 미리 받는 게임 파일), 다른 도메인 이미지는 200 또는 불투명 응답, 데이터(JSON)는 200만.
  - 이미지 캐시 `lckc-img-v3`로 교체, 설치 즉시 `skipWaiting()`, 활성화 때 `clients.claim()` → 새 서비스 워커가 바로 적용되고 예전 캐시는 지워짐. 업데이트로 바뀐 경우에는 "새 버전이 적용됐어요 · 새로고침" 알림.
- **이미지 로더 (`js/ui/imgLoader.js`)**: 매 시도마다 먼저 CORS(`crossorigin="anonymous"`)로, 실패하면 같은 주소를 일반 `<img src>`로 한 번 더. 그래도 안 되면 1·3·8초 재시도 → Community Dragon → 이니셜.
- **디버그 패널**: 실행 모드(홈 화면 앱 / 브라우저 탭, `navigator.standalone` 또는 `display-mode: standalone`)와 서비스 워커 버전·이미지 캐시 이름 표시, CORS 없이 받은 개수.
- **설정 → 🧹 캐시 초기화**: `lckc-` 캐시 전부, Data Dragon 데이터 캐시(`lckc.ddragon`)를 지우고 서비스 워커 등록을 해제한 뒤 새로고침. 세이브·설정은 그대로.
- **타이틀 → 불러오기**: "홈 화면 앱과 사파리는 저장 공간이 따로예요" 안내 한 줄과 바로 옆에 "세이브 코드 붙여넣기" 버튼.
